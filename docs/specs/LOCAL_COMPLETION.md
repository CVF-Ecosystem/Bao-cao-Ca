## Local outcome and safety invariants

A user can open the existing app, explicitly upgrade a supported existing local data set with a verified recovery copy, use/save/correct and inspect its history, obtain tiered recoverable backups, perform safe explicit maintenance, and use the improved desktop UI/print flows. All existing reports, revisions, data, attachment hashes, staff/catalogs, backup identity, correction copies, and optimistic version conflict checks survive. Source and fixture tests must demonstrate behavior on disposable roots only; no production data or automatic adoption/migration. Restore/adopt/review paths must classify a DB before writable open and refuse unknown or malformed versions without changing the source. Old 1.9.x refuses schema 4; user guidance requires all machines upgraded together and identifies the recovery copy.

### Migration and recovery

- New empty stores may initialize schema 4. An existing schema 3 DB is opened only after explicit local upgrade action: preview source identity, schema, expected pre-upgrade copy and consequences; user initiates once through existing local UI/launcher. Refuse change when another session owns the data directory or source identity/stamp changed after preview. Schema 1/2 remain readable for inspection where already supported and require explicit verified stepwise migration through schema 3 to 4, with per-source pre-upgrade copies and recovery; never silently upgrade any existing schema. Every supported legacy version and recovery path must be tested. Unsupported/invalid schema and corrupt/absent original fail closed; no blank DB substitution.
- Under existing session lock and SQLite-consistent snapshot, create `_TRUOC_NANG_CAP_3_4.db` in a safe same-dataset location, refuse to overwrite existing different backup, full-verify identity, contents and hash before starting; retain original copy and report its location. Perform schema upgrade transactionally and atomically mark version 4 only after columns/data are valid; interruption, insufficient disk/permissions, existing backup collision, failed DB integrity, schema mismatch and version race leave original recoverable, no false success. Restart and restore from backup are tested; cannot claim atomicity against hostile external file changes or power loss beyond evidence. Migration is never performed on uploaded/read-only review sources. Preview/restore of supported older backups must not silently mutate them; explicit, separately confirmed recovery/upgrade path preserves both prior main and selected backup.
- `revisions`: `kind` non-null default `legacy`; `os_user` nullable, desktop value acquired server-side (`getpass.getuser()`), and `auth_user` nullable/reserved, never supplied by local browser or treated as authenticated identity. Historical rows preserve count, payload, version, timestamp, actor and reason exactly; no merge. Shared OS accounts do not identify individuals.

### D3 revision and correction contract

- `/api/save` accepts `save_kind=auto|manual|close|correction` and validates server-side against actual old/new state and DB mode; closed records reject auto, correction copies permit correction only, closed corrections retain reason and closed status. Local browser sends the appropriate kind; reject invalid/missing kinds rather than infer when new API is invoked. A `BEGIN IMMEDIATE` transaction checks expected report version before mutation and writes reports/revisions atomically.
- Consecutive changed draft auto revisions coalesce only when preceding revision is auto, actor and both identity fields match, and not a review-copy. Changed saves advance report version; coalesced revision moves to that version. A no-content-change manual save marks the latest auto revision manual without increasing version, after version checking; do not alter old legacy/closed/correction entries. Manual/close/correction and identity changes create separate history. After every commit last revision version and payload match report; gaps are allowed. Exact oracle: ten autos → v10 auto; changed manual → v11 manual; five autos → v16 auto; unchanged manual promotes v16; three autos → v19 auto; changed actor auto → v20 auto; close → v21 close: exactly six rows v10,v11,v16,v19,v20,v21. Two concurrent clients with same version cannot both commit (409 for loser).
- A schema-3 correction copy remains readable without mutation and imports each revision since `correction_base` with `kind=correction`, original actor and original source bytes retained; schema-4 correction copies preserve every correction with explicit kind; verify all blobs/hash and apply target conflict recheck inside same transaction. Test differing and gapped source revisions, same/conflicting base, rollback on missing or corrupt blob, source immutability and before/after reports/history. Display history `kind`, OS user with identity caveat, and adjacent revision diff; do not claim real-user authentication.

### D2 backup scheduling, retention and validation

- Factor validation/schedule through existing `Protection` and `snapshot` ownership. `full`: SQLite integrity_check, report/revision/correction payload and date/shift integrity, rehash every blob. `quick`: quick_check and equivalent structural/payload validation, rehash every blob absent from verified cache. Cache is keyed by dataset identity and verified blob identity, persisted atomically only after successful verification, invalidated on restore/adoption/migration/identity change; treat cache as a speed optimization, not evidence against later bit-rot. Never skip mandatory full validation on receipt, adoption, restore preview/restore or explicit user backup.
- Automatically schedule startup and close quick unless no successful full or full overdue after 24 wall-clock hours since the last successful full snapshot, evaluated only when the app next runs; draft saves/attachment/catalog backup quick at existing 5-minute gate. Forced full bypasses automatic throttle. Persist the last successful full wall-clock timestamp; missing/corrupt timestamps or clock rollback force full. Downtime counts toward overdue age, but no action runs while the app is stopped; this satisfies the original startup-after-days acceptance without a new active-time accounting mechanism. Successful full pin records verified path/name, time and database_id only after a complete verified snapshot and durable metadata. Prune keeps last valid full pin until a newer verified full is durably pinned, in both local/external destinations independently; failure retains prior full and memento, signals error and never labels quick as full. If external drive unavailable, retain local verified snapshot and old external marker. Display last successful full and relevant warning; restore/adoption/full verification clear stale cache and do not advance marker on failure. Reuse existing space and atomic-file checks; do not run concurrent backups against same destination.
- Test synthetic wall clock with downtime/restart/24-hour equality, 5-minute throttle and forced bypass; cache hit/new blob and invalidation per dataset; corruption of previously cached blob goes undetected by quick where expected but full fails; last-good full survives prune across simulated days and failed replacement. Verify failure at snapshot/check/fsync/config/prune/external disconnect/space boundary leaves DB and last-good backup readable and warnings accurate. Large-data timing and machine/storage environment recorded, no unsupported speed threshold or human speed claim.

### D4 safe maintenance

- Viewer copies: safely recognize regular files directly under `DB_KIEM_TRA` without following symlink/junction/escape; only known original viewer-only copies older than a proposed 30 days are eligible, excluding currently open and pending-import sources. Validate read-only metadata and identity immediately before any deletion; unknown/corrupt/in-use files are retained and reported. A correction-enabled copy is never automatically deleted regardless of age/restart. Explicit deletion only after verified export/import of that exact copy and informed operator selection; if no durable evidence can establish this, retain it. A dry-run lists only derived metadata, no report contents; revalidate file identity and pending/open status at execution. Scope and exact threshold require work-order admission.
- Orphan blob maintenance is explicit user-invoked with preview/confirmation, not auto on backup. At confirmation, create and fully verify a new same-dataset snapshot containing every blob that could be deleted, and retain that snapshot. Recheck source identity and state under the maintenance transaction; any change after the verified snapshot aborts deletion. A historical full marker alone is insufficient. On a single `BEGIN IMMEDIATE` transaction, re-evaluate all references from reports, revisions and correction_base; preserve pending newly uploaded blobs with an age threshold (proposed 24h). Refresh `uploaded_at` on identical re-upload in the same owner transaction. If any payload is unreadable/ambiguous or identity/context/preview changed, delete nothing. Preserve blobs referenced solely by history/correction_base or pending age; cancellation and failed verification cause no delete. Concurrent save/upload versus maintenance must serialize and recheck; no `VACUUM` bundled or implicit. Report internal space reclamation separately from actual filesystem shrinkage.
- Quarterly restore drill into a disposable separate directory verifies full snapshot, integrity, identity, report/revision/blob counts and selected example content without modifying the main DB or existing backup; record date and result locally, provide guided on-demand operation and overdue reminder. No unattended overwrite or invented claim a restore occurred. Retention deletion, restore drill and DB maintenance require interruption, failure, duplicate/hash and simultaneous-client tests.

## Integration contract for independently owned server and UI

These field names are the joint interface locked by Root before dispatch. Explicit per-dataset migration confirmation is a development safety choice within the authorized migration scope, not a newly invented operator instruction. Every POST below requires the existing session cookie, exact Host, `X-Ca-Request: 1`, same-origin policy, JSON content type, strictly typed fields with unknown fields rejected, and matching context. Existing read-only/review-copy restrictions remain enforced server side. Responses are JSON and errors preserve existing `error` text with stable `code`: 400 `INVALID_INPUT`; 403 `FORBIDDEN`; 409 `STALE`/`CONFLICT`/`UNSAFE_STATE`; 413 `LIMIT_EXCEEDED`; 500 `OPERATION_FAILED`/`RECOVERY_REQUIRED`. Never send SQL, stack trace, secret, local full path, report contents in logs, or claim success after failed verification. All preview handles are random >=128-bit, server-owned, one outstanding per operation/session, 300-second monotonic expiry and single use; replacing preview, context change, cancellation, expiry or failed confirm clears it. Confirm only accepts context+nonce; exact selected objects and fingerprint are held server side. Recheck type/identity/dataset/context, file stamps, active/pending locks and necessary transactional state immediately before effects; reject stale state and require a new preview. Pending UI responses use generation/context/dialog guards.

- `GET /api/info` extends existing response with `schemaVersion: string`, `capabilities: {saveKinds: boolean, revisionDiff: boolean, hideShips: boolean, backupLevels: boolean, maintenance: boolean, migration: boolean}` and `lastFull: {at: string, databaseId: string, location: "local"|"external"}|null`; disabled/unavailable UI is driven by capabilities, never by optimistic client assumption. Values describe this context, not authorization for a different store. Migration-required startup has a restricted session that permits only status, safe migration preview/confirm and shutdown; no writable `Store` construction or report mutation before explicit successful migration. Expose no passwords/keys.
- `POST /api/save` `{context:string, report:object, version:integer, reason:string, save_kind:"auto"|"manual"|"close"|"correction"}` returns existing saved report shape; `version` rejects booleans. Context/expected version and allowed kind vs actual stored status are checked atomically under the report transaction. Desktop `os_user` obtained locally by server; browser-supplied identity keys are forbidden. No-content manual promotion returns unchanged version and payload.
- Existing `GET /api/history?id=<report-id>&context=<context>` adds to each existing row `kind:string`, `os_user:string|null`, `auth_user:string|null`, retains `version`, `saved_at`, `actor`, `reason`, `payload` and order newest first. Absent predecessor displays no comparison; client compares exact adjacent list elements rather than assuming consecutive versions. Do not render auth_user as authenticated local actor. For correction comparison, existing `corrections-preview` returns `current`, `incoming`, `base_version` and required source identity; the same deterministic, escaped UI comparison component accepts two report payloads and renders field paths with changed values (and absent-vs-empty distinctly). Source report data never becomes HTML without escaping.
- `POST /api/ships-hide` `{context:string,name:string}` validates an existing active catalog ship and returns `{ships:[string,...]}` after setting its existing `active=0` in a transaction. Existing historical report payload unchanged. Absent/inactive returns 409; an explicit later user add may reactivate via existing owner. Readonly/review contexts return 403 or 409 according to existing main-store policy consistently.
- `GET /api/protection` retains existing status, extends `last_full_local` and `last_full_external` to `{at:string,name:string,database_id:string}|null`, plus `last_validation:"quick"|"full"|null` and existing `warning`, `warning_level`. No old local/external status field removed. The status must only reflect a completed, verified snapshot; force-full request is existing `/api/protection-backup` `{context}` and respects the full policy.
- `POST /api/schema-upgrade-preview` `{context:string}` returns `{sourceSchema:"1"|"2"|"3",targetSchema:"4",databaseId:string,backupName:string,migrationSteps:[{fromSchema:string,toSchema:string,backupName:string}],nonce:string,expiresInSeconds:300}`. The actual sourceSchema and ordered migrationSteps are derived from the inspected supported source; no step runs before consent to the entire displayed path. The session is restricted and selected DB is fixed by the launcher's configured dataset, not an arbitrary client path. `POST /api/schema-upgrade-confirm` `{context:string,nonce:string}` returns `{schemaVersion:"4",databaseId:string,backupName:string,context:string}` only after the verified-copy and migration succeed; new context invalidates all prior plans. On failure, return stable failure code and `backupName:string|null`, retaining evidence and source as specified; explicit separate recovery screen selects known backups, never arbitrary caller path. New empty dataset is initialized directly as 4 only when the existing no-white-database guard permits genuinely first use.
- `POST /api/maintenance-preview` `{context:string,kind:"viewer_cleanup"|"orphan_blobs"|"restore_drill"}` returns `{kind:string,items:[{id:string,label:string,eligible:boolean,reason:string}],count:integer,nonce:string,expiresInSeconds:300}`. IDs are opaque, server-generated, bounded and cannot specify paths/hashes; only eligible items contribute to confirm. Viewer cleanup cutoff 30 days and blob cutoff 24 hours use injectable clocks; malformed timestamps/identity/classification exclude items. Blob preview includes count/total bytes as metadata, no data contents. Restore drill has one synthetic destination determined by app beneath a safely owned temp parent; no target path accepted. `POST /api/maintenance-confirm` `{context:string,nonce:string}` returns `{kind:string,completed:integer,retained:integer,message:string}` with no report data; no partial success hidden. A separate cancel `{context:string,kind:string}` at `/api/maintenance-cancel` clears pending. Maintenance only on writable main DB; a new fully verified same-dataset snapshot is required at confirm, includes all candidate blobs and is retained; failed snapshot/verification or a changed source aborts without deletion. Revalidate all blob references in one `BEGIN IMMEDIATE` transaction and roll back on any malformed record, stale plan or SQLite failure. File cleanup cannot promise multi-file transactional delete: on a mid-batch error stop, return explicit completed/retained counts and preserve unknown files, never report all succeeded; each selected entry identity is rechecked immediately before unlink and cross-process races documented.
