# Personnel Excel catalog import — draft specification

Status: SPEC_LOCKED — independently audited design; implementation still requires exact-action admission. Date: 2026-11-08.

## Outcome and scope

Deliver E1–E6 of `docs/roadmaps/TAN_THUAN_PORT_ADOPTION.md` as one usable additive personnel catalog import. The user chooses a local flat `.xlsx`, sheet, header row and columns, inspects an explicit row-level plan, and confirms adding eligible names to the existing main catalog. This uses the existing catalog owner and context/digest checks; no direct `people` writes, schema, identity, auth, team, assignment template, report/revision or cross-project synchronization change is authorized. E7 team mapping and all other roadmap/product acceptance remain separately owned. This draft is neither an admitted milestone registry nor a work order.

## Input contract and interaction

- Only unencrypted macro-free `.xlsx` flat tables are supported; reject `.xls`, `.xlsm`, encrypted/malformed archives, external relationships, unsupported features and merged cells intersecting the selected header or data range. No formula evaluation; reject formulas in any mapped cell, even if cached. Reject sheet names or cells that cannot be safely represented. Never execute workbook content; render as text with HTML escaping.
- Server enforces compressed upload <= 2 MiB; <= 128 ZIP members, <= 16 MiB aggregate actual inflated bytes, <= 4 MiB per member, ratio <= 100:1, <= 10 sheets, <= 2,000 rows and 64 columns per selected sheet, <= 500 data rows, <= 1,000 characters per inspected cell. Enforce while reading, independently of advertised sizes/dimensions, before expensive parsing; reject duplicate/case-colliding ZIP members, unsafe paths, malformed relationships, DTD/entities and archive bombs. Do not trust client validation or ZIP metadata alone. Limits are provisional engineering choices for review, not proof of performance.
- Permit sheet, 1-based header row and distinct mapped columns; name required, code/title/group optional and explicitly shown as transient. Recognize the four template headers `MSCĐ`, `Họ và Tên`, `Chức danh`, `Nhóm/Ca` without mapping title to department or group to a team. Suggestions are exact normalized known labels, never silent substring inference; user explicitly confirms mapping. To prevent report data masquerading as personnel, require a recognized personnel-name header plus a recognized employee-code, job-title or personnel-group header on the selected row even when manual mapping is used; no override for a report-shaped file. Reject known three report workbook structures in E1 tests. This conservative profile can reject legitimate unfamiliar tables; expanding it is a separately reviewed contract change.
- File remains in memory only for bounded preview/confirmation, never persisted or logged. Show sheet, source row, mapped fields, exact names to add, names already present, errors, warnings and totals; display clearly that only names persist, other fields do not, and identity is name-only. User selects individual rows to exclude and regenerates preview; exclusion is explicit, visible and retained in that preview. Empty selected plan or any remaining invalid/conflicting row prevents confirm. Cancel, close, timeout or error causes no catalog/DB write.
- Normalize name with NFC and trim boundary whitespace consistent with `parse_lines`; casefold determines exact duplicate against the current catalog and file. Do not strip accents to identify people or merge approximate matches; warn when NFD-decomposed names with combining marks removed and casefolded match an existing name but their NFC casefolded names differ; never silently merge or rename. Name limits and validation are existing `parse_lines` requirements (1–120 characters, no control characters or semicolon, <= 500 catalog names). Duplicate normalized names within selected file and different codes sharing a name or same code paired with different names are blocking row errors. Blank names, non-text name and invalid mapped cell types block with sheet/row/column. Text codes retain leading zeros; numeric codes are explicitly unsupported and block instead of guessing display formatting. Code is only a same-file consistency check; it cannot detect a renamed person across imports. Missing codes are allowed if no code column is mapped; a mapped code must be text and nonempty for every selected data row.
- Preview records source bytes hash, selections, exclusions, immutable normalized plan, catalog raw digest and current DB context in a bounded server-owned, single-use expiring nonce. Confirmation carries only nonce/context; server revalidates authorization, writable main-store identity, context, digest, bounds, plan and conflicts immediately before save. A changed file/selection requires new preview; expired, replayed, altered or stale plans fail closed. At most one bounded pending import per session; replace or clear it on cancel/context change. No client-supplied catalog text may bypass server plan validation. Ordinary same-process requests are currently serialized by `HTTPServer`; external file changes still require digest recheck and a test for the race boundary.

## Persistence and failure contract

Use the additive `Catalogs` owner operation defined below, reusing existing validation, backup and synchronization rules. Current `save` serializes all five files and `sync` replaces DB people with `active=1`; the additive operation preserves other catalog file bytes and refuses inactive or inconsistent states before writing. E3 requires tests on non-default catalogs, inactive people and existing report/revision snapshots. Existing entries missing from workbook remain unchanged; repeated import is a no-op without duplicate names. Only newly added people may be active. No automatic team assignment.

A stale digest or switched context fails without writing. Backup creation/read failure aborts before replacement. For write/DB failures, return an error, retain and identify a usable pre-import backup, attempt restoration and verify resulting file/DB consistency; if restoration itself fails, explicitly report partial/unknown state and recovery path and never report success. Abrupt crash atomicity is not promised; prove ordinary injected failures and recovery, including backup creation, replacement, DB sync, restore failure, permission/space errors. Because the existing method's rollback can itself fail and its backup stage occurs outside its try block, a targeted owner-level safety correction may be needed; scope and exact edits require the work order and independent review. Do not claim guaranteed recovery when the backup cannot be created or accessed.

## Exact HTTP and session contract (draft for admission)

All four endpoints are POST JSON, use existing Host/cookie, `X-Ca-Request: 1` and Origin checks, and require a writable main DB (`store is main_store` and not readonly) plus current `context`. No endpoint is available in viewer or review-copy mode. Unknown/missing fields, wrong types, duplicate JSON keys and invalid base64 return 400. Responses are UTF-8 JSON with `Cache-Control: no-store`; successful responses contain the fields specified below. Every error is `{ "error": string, "code": string, "sheet": string|null, "row": integer|null, "column": integer|null }`; no raw workbook data, paths or secrets in errors. Authentication/origin violations return 403 `FORBIDDEN`; stale context/digest, expired/consumed nonce or concurrent modification return 409 `STALE`; unsafe inactive or inconsistent catalog state returns 409 `CATALOG_UNSAFE`; invalid workbook/mapping/rows return 400 `INVALID_INPUT`; over-limit requests return 413 `LIMIT_EXCEEDED`; persistence failures return 500 `SAVE_FAILED` or `RECOVERY_REQUIRED` as specified below. Blank omitted location is null. All source indices are 1-based physical Excel row/column indices, not zero-based array offsets; sheet is the exact workbook sheet name.

Transport: `Content-Type: application/json`; declared body <= 3 MiB, strict RFC 4648 base64 string `fileBase64` decoded server-side to 1..2,097,152 bytes with no whitespace; never rely on filename, extension, MIME, browser validation or content-length alone. Exactly 3,145,728 bytes body cap covers base64 plus bounded mapping/row data and stays below existing 4 MiB cap. Server rejects an incomplete body and excess input before parse. Hash decoded workbook bytes with SHA-256. Requests do not include local paths. File bytes are resent with every inspect/preview, bounded in RAM and discarded after processing; no workbook bytes are held in the nonce, written to disk, logged, or returned. All ZIP members and all sheets are preflighted before `openpyxl.load_workbook`, even sheets not selected: the archive-level limits in this spec apply across all members; each worksheet XML must be streamed under the aggregate limits, with physical coordinates <= 2,000 rows and 64 columns, <= 1,000 characters per cell, and duplicate coordinates invalid. Do not trust dimension metadata. Reject high sparse coordinates, even if the number of actual rows is small. During inspection provide at most 10 sheets, first 20 physical rows and first 20 columns, including gaps; each display value is a raw JSON text string capped at 1,000 characters; the UI escapes it exactly once when inserting into HTML. Reject unsupported structures before disclosing samples.

1. `/api/personnel-xlsx-inspect`: request `{context: string, fileBase64: string}`. Response `{fileSha256: string, sheets: [{name: string, sample: [{row: integer, cells: [{column: integer, value: string}]}]}]}`. Empty cells may be omitted, physical indices preserved. Inspection is read-only and does not create a nonce. `sample` contains only the bounded first 20 by 20 region.
2. `/api/personnel-xlsx-preview`: request `{context: string, fileBase64: string, expectedFileSha256: string, sheet: string, headerRow: integer, columns: {name: integer, code: integer|null, title: integer|null, group: integer|null}, excludedRows: [integer]}`. SHA-256 must match decoded bytes. `headerRow` must be 1..2,000; distinct mapped columns 1..64; excluded rows unique, sorted by server, > header row and <= 2,000; a row index not present as a nonblank mapped-data row is invalid. The selected table covers rows after the header through the highest row containing any mapped value. A row is ignored only if all mapped values are empty/whitespace; a nonblank optional field with blank name is an error. Count all nonblank mapped rows, including excluded rows, against 500. Excluded rows appear with status `EXCLUDED` and count toward totals; a user may exclude an invalid or conflicting row, but structural workbook errors and invalid mapping always block. Recompute duplicate/conflict checks on included rows only. A duplicate file name is a blocking conflict for all included rows participating; one can be explicitly excluded to resolve it. Near-name warnings never block or merge and require the user to see them before confirming; exact normalized catalog match is `EXISTING`, casefold match preserves existing spelling. Response `{fileSha256: string, sheet: string, headerRow: integer, columns: object, counts: {new: integer, existing: integer, error: integer, excluded: integer}, rows: [{row: integer, name: string|null, code: string|null, title: string|null, group: string|null, status: "NEW"|"EXISTING"|"ERROR"|"EXCLUDED", messages: [string]}], canConfirm: boolean, nonce: string|null, expiresInSeconds: integer|null}`. Every nonblank row has one status; escaped rendering is a UI duty, text is not HTML. `canConfirm` is true only when there is at least one NEW row and no included ERROR. No new rows means a valid no-op preview with `canConfirm:false`, no nonce; the UI explains that nothing needs adding. `nonce` is cryptographically random, >= 128 bits, opaque; the server retains only immutable validated plan, hash, context and digest, never raw bytes. A new preview invalidates the prior plan, including an invalid/error preview.
3. `/api/personnel-xlsx-confirm`: request `{context: string, nonce: string}`. A nonce expires 300 seconds after successful preview using a monotonic clock, is single-use, and is consumed before any save attempt, including failed attempts. No body-supplied names, digest or workbook may override the server plan. Recheck context, writable main store, current raw catalog digest and the owner preconditions below immediately before mutation. On success return `{added: integer, existing: integer, fileSha256: string}` using the server plan; do not return success if backup, write, sync or verification fails. Stale/error requires a fresh preview. Same-session request handlers are serialized by the current `HTTPServer`; it is not a cross-process filesystem lock, so check digest just before replacement and verify after; do not claim immunity to arbitrary concurrent external editors.
4. `/api/personnel-xlsx-cancel`: request `{context: string}`. Clear any pending plan; response `{cancelled: true}` even if none was present. UI calls it on explicit cancel/close; timeout, server shutdown, context/DB change, new preview and successful/failed confirmation also clear the plan. Browser disappearance is handled by expiration, not a claim that the server receives a close event. At most one pending plan for the application's session, including all tabs.

## Exact additive-owner behavior

Choose the smallest safe owner extension: a `Catalogs` additive people operation that reuses existing validation, raw digest, backup and sync rules, writes only `NHAN_VIEN.txt`, and is invoked solely with the server-generated confirmed plan. Existing generic `Catalogs.save` behavior remains available for ordinary editing; do not feed it five files and pretend it preserves untouched bytes. Precondition immediately before backup and again immediately before replacement: all five catalog files are readable and valid, digest equals preview; the active main DB catalog snapshot is consistent with parsed catalog values, DB people contain exactly the file's normalized names and every `active` flag is 1; roles/jobs/team/template semantics agree with the catalog owner’s resolved values. Any inactive, missing, extra or inconsistent person/catalog state returns 409 `CATALOG_UNSAFE` without a write, explaining the catalog must be reconciled through its existing owner. This is deliberately a refusal, not reactivation or automatic repair. Thus no inactive person can be changed by this import.

Validate the union via existing `parse_lines`, existing team/template validators, and all limits. Capture byte-for-byte originals for all five files and required pre-import DB observations. Create a uniquely named retained backup of all five originals, verify readable exact bytes before replacing anything; if backup creation/verification fails return `SAVE_FAILED`, no catalog or DB writes. Write temporary people file in the same directory, flush/close and replace; never write the other four catalog files. Execute existing `sync` and verify expected people (all prior names plus new, active=1), unchanged roles/jobs/team/template DB semantics and byte-identical four non-people files. Report and revision preservation is verified in tests, not by scanning the production history during each import. Catalog digest metadata is allowed to change. A no-op is not sent to save.

On a failure after replacement, compare the current people-file hash with the exact bytes just written by this operation; if it differs or cannot be read, do not overwrite the possible external edit and return `RECOVERY_REQUIRED`. Otherwise restore the original people bytes from the verified backup, re-run owner sync, then verify file hashes and DB catalog equivalence to the pre-import snapshot. Return 500 `SAVE_FAILED` only when verified restoration succeeds, with a user-safe recovery message and backup identifier. If restoring or verifying fails return 500 `RECOVERY_REQUIRED`, preserve the backup and report its project-local backup identifier and the need to stop editing and restore through the existing recovery process; do not assert the prior state was recovered. The error object may additionally carry `backupId: string|null` (opaque generated identifier, not a filesystem path). The four other files must remain byte-identical in both success and attempted rollback. A failure before a verified backup may leave an incomplete backup directory, but no catalog/DB mutation. Power loss and hostile simultaneous external writes are outside transactional guarantees; independent tests must show detected conflicts and characterize remaining race limits rather than claiming atomicity.

### Header and display normalization

For header suggestions/eligibility only, trim, NFC-normalize, collapse runs of whitespace to one space and casefold; no accent removal or substring matching. Accepted aliases are: name `họ và tên`, `họ tên`, `tên nhân viên`; code `mscđ`, `mã nhân viên`; title `chức danh`; group `nhóm/ca`, `tổ nhân sự`. A selected name column's header must be one name alias and at least one other mapped column must have an alias of its own semantic role; ambiguous duplicate matches are never auto-selected. Manual selection chooses among eligible columns and sheets/header rows, but cannot remap unrelated headers into a personnel role. Empty strings and whitespace-only strings are blank; formulas are never blank. Other typed values are displayed safely but invalid in mapped fields unless explicitly accepted by this spec. This contract is intentionally conservative and can be expanded through a separately reviewed change.

## Reader and server integration contract

The isolated reader/planner exposes `inspect_workbook(blob: bytes) -> dict` and `build_plan(blob: bytes, sheet: str, header_row: int, columns: dict, excluded_rows: list, existing_names: list[str]) -> dict`. `inspect_workbook` returns `{sheets: list}` with the sheet list specified for the inspect response; handler computes file hash. `build_plan` independently re-preflights the entire supplied byte string, validates the selected headers and cells, then returns `{sheet, headerRow, columns, counts, rows, canConfirm, newNames}` with the response semantics above; `newNames` is an internal-only ordered list of exact normalized additions and never accepted from the client. The handler adds SHA-256 and creates the nonce only from the returned validated plan and current catalog. Invalid workbook or mapping raises `PersonnelXlsxError(code, message, sheet=None, row=None, column=None)` exposing those same safe attributes; handler maps it to the HTTP error contract without returning tracebacks. Functions are pure with respect to filesystem, network, catalog, database and server state; inputs and outputs remain bounded as above. Server independently enforces authorization, context, digest, single-use lifecycle and owner preconditions. Formula in any mapped cell, including an excluded row, is an unsupported workbook error; excluded rows can resolve row-level name/code validation errors and duplicate conflicts, never structural or formula errors.

The inactive-state refusal must be tested directly on the actual owner precondition, including a database made inactive after startup. Existing startup sync may itself alter prior states; this feature does not claim to change or correct startup behavior. The hash-before-restore check is not a cross-process lock and cannot eliminate a write between check and replacement; document that residual race.

The reader must disable or refuse an unsafe ambient lxml path before the first openpyxl import and verify actual parser provenance and defusedxml activation; if an incompatible already-loaded state prevents this, fail closed. Verify the packaged runtime parser, not just an environment variable.
