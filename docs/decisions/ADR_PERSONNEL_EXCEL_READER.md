# ADR: reader for personnel Excel import

Status: ADR_LOCKED — independently audited design; implementation still requires exact-action admission. Date: 2026-11-08.

## Decision proposed

Use a pinned maintained Python `openpyxl` reader, proposed version 3.1.5, server-side for bounded `.xlsx` inspection. Pair it with pinned `defusedxml` and verify that the packaged runtime actually uses hardened XML handling; use `data_only=False`, reject formula cells rather than evaluate/cached-value trust, do not preserve or execute VBA, and reject external links/relationships before library loading. A preflight implemented with standard-library ZIP and hardened XML parsing must enforce actual decompressed limits and reject duplicate/path traversal members, encrypted or macro-containing packages, unsupported relationships, excessive sheets/rows/columns/cell lengths, and merged selected table ranges. A ZIP metadata check alone is insufficient. These controls and the proposed limits are specified in `docs/specs/PERSONNEL_EXCEL_IMPORT.md` and must be tested against malicious and representative files.

This is a proposed engineering choice, not a declaration that installing a library makes untrusted files safe. Reject input outside the deliberately narrow profile; no formula recalculation, legacy XLS, arbitrary report sheets, or general Excel compatibility is promised. Use transient bounded bytes and server-owned short-lived preview plans; no personal workbook saved/logged.

## Evidence and tradeoffs

Current project `pyproject.toml` declares standard-library Python 3.9+; `cong_cu/DONG_GOI.py` installs unpinned PyInstaller, insists on a clean Git tree, and invokes one-file packaging; `SO_BAO_CAO_CA.spec` has no explicit spreadsheet dependency. Local read-only inventory found Python 3.11.9, openpyxl 3.1.5 (installed metadata says MIT), defusedxml present and PyInstaller 6.14.2. Local presence is not a declared dependency, reproducible installation, security review, or proof EXE bundles it. Confirm actual package licenses, transitive dependency pins, supported Python versions, current advisories and exact release hashes from primary sources before admission; record result and any exposure/mitigation. A release/build dependency mechanism, exact packages and lock/hashes, license notices and PyInstaller collection must be owned in the implementation order and verified on a clean supported Windows build. `defusedxml` is mandatory for this proposal; do not silently fall back when missing. Local version observations do not establish a safe pin.

Alternative: build a custom standard-library OOXML reader, preserving the no-dependency baseline. Rejected for this proposal because shared strings, XML namespaces, relationships, worksheets and malformed archive handling substantially expand correctness and security work and still need bounded parsing; it would duplicate a mature reader. Browser-only parsing is rejected because independent server revalidation is required. A mature reader without explicit preflight is rejected because it does not itself establish bounded resource use or the product's narrow acceptance semantics.

## Consequences and gates

Dependency addition changes the baseline and requires exact-action admission, independent review, hermetic/security fixtures and packaged-EXE product proof. The existing 4 MiB HTTP default cap must not be circumvented; the proposed 2 MiB workbook cap must include a separately bounded transport envelope. All five catalog files are rewritten by the present save owner and the DB sync replaces people with active rows; preservation and rollback are unproven and required independently of reader choice. The Windows release builder needs a clean commit, hence build/test evidence must identify that commit and executable; no skip becomes PASS. Stop and re-assess if the safety wrapper, runtime package, preservation or limits cannot be verified within the approved work order.

## Primary-source review (2026-11-08)

[openpyxl package metadata](https://pypi.org/project/openpyxl/) identifies 3.1.5 and explicitly recommends defusedxml for XML expansion attacks. [defusedxml package metadata](https://pypi.org/project/defusedxml/) describes its hardened XML functions; propose pin 0.7.1, subject to the dependency and license review above. The [openpyxl XML selection source](https://openpyxl.readthedocs.io/en/latest/_modules/openpyxl/xml.html) includes the `OPENPYXL_DEFUSEDXML` switch: fail closed if hardened parsing is disabled/unavailable, verify the actual parser path in the packaged artifact, and do not depend on ambient lxml selection. [PyInstaller hooks documentation](https://www.pyinstaller.org/en/stable/hooks.html) explains collection hooks for dynamic imports; package collection remains a tested outcome. These references do not establish an absence of vulnerabilities or replace bounded decompression and XML preflight.

## Candidate dependency set and environment

The candidate exact runtime set is openpyxl 3.1.5, defusedxml 0.7.1 and et-xmlfile 2.0.0. The Windows build-only set is PyInstaller 6.14.2, altgraph 0.17.4, packaging 24.2, pefile 2023.2.7, pyinstaller-hooks-contrib 2025.5, pywin32-ctypes 0.2.3 and setuptools 84.1.0. Pin and hash the release artifacts using [dependency-source-review.json](../reviews/personnel-import-20261108/dependency-source-review.json), which records official-source versions, licenses, hashes, reported advisories and limitations. Setuptools 78.1.0 was rejected based on its reported advisories; 84.1.0 is the proposed patched candidate, not an independent security certification. The build-only toolchain requires Python >=3.10 and is to run in a fresh isolated Python 3.11 environment using hash-verified wheels only; the application runtime compatibility target remains Python 3.9+. The 3.9 runtime target is not yet executed or proven. Do not install dependencies before exact BUILD admission. Independent acceptance of this candidate set remains with the reviewer. Frozen packaging must include distribution metadata for any runtime version checks and verify actual parser provenance.
